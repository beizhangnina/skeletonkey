# v0.1 acceptance: what "done" means

## North star

A developer should **not** have to sign up for a key-aggregator service to let
their agent use a paid API.

Their own agent — Codex, Claude Code, anything that speaks MCP — plus SkeletonKey
should be enough:

1. the agent **finds** the right API (`find_api`),
2. gets **access just-in-time** (`request_access` → agent-assisted signup with
   the agent's own browser and the agent's own email, **the human confirming the
   final step**),
3. and **calls it through the proxy**, never holding the key.

No aggregator account, no third party holding the credential, no monthly fee for
the privilege of key storage. The key lives in the developer's own vault
(Bitwarden, 1Password, OS keychain, or an encrypted file), the billing
relationship is theirs, and the proxy is a local process they can read.

What SkeletonKey explicitly refuses to become: a service. There is no SkeletonKey
account, no SkeletonKey server, nothing to sign up for, and no network traffic other
than the upstream API call the agent asked for.

## What is actually in v0.1

**In:**

- Pluggable vault adapters: `bitwarden` (default), `1password`, `keychain`,
  `encrypted-file`. The plaintext `file` backend is test-only and refused
  without `SKELETONKEY_ALLOW_TEST_BACKEND=1`.
- `keys.yaml` metadata index with no secret values.
- The injecting proxy, in reverse (`/<domain>/<path>`) and forward (`HTTP_PROXY`)
  modes, with client auth headers stripped.
- Gateway mode for multiple devices: `--gateway`, Tailscale-first binding, a
  shared `X-SkeletonKey-Token`, and a refusal to bind `0.0.0.0` without
  `--allow-all-interfaces`.
- The SQLite ledger: one row per call, with `cost` populated only when the
  upstream actually reported a price.
- The MCP server (`skeletonkey mcp`) with seven tools, none of which can return a
  secret.
- `apis.yaml` plus a validator that rejects guessed prices.
- The agent skill in `skills/skeletonkey/SKILL.md`.

**Out (and honestly so):**

- **Payments.** No virtual cards, no crypto rails, no top-ups. Phase 2. In v0.1 a
  human pays with their own card; SkeletonKey code never touches card data.
- **Agent-driven signup.** SkeletonKey produces the *plan* and stores the result. It
  does not drive a browser or read email — the agent's own computer-use and
  email connectors do that, and v0.1 does not automate them for you.
- **Real cost attribution.** `cost` is `NULL` for almost every provider, because
  almost none report per-call cost in a response header. A `NULL` is the honest
  answer.
- **Rotation, budgets, discovery scans.** See the README roadmap.
- **Verified `apis.yaml` data.** Every row shipped in this repo is
  `example: true` with `min_topup: null` and `checked_date: null`. Nobody has
  verified a price or a terms-of-service clause, so the file claims nothing.

## Acceptance checks

| # | Check | How |
| --- | --- | --- |
| 1 | A key can be stored and used without any code seeing it | `./scripts/demo.sh` |
| 2 | Secrets never reach metadata, logs, or the ledger | `npm test` (`keys.test.ts`, `proxy.test.ts`) |
| 3 | The encrypted vault round-trips and leaves no plaintext on disk | `npm test` (`vault-encrypted.test.ts`) |
| 4 | No MCP tool can return a secret | `npm test` (`mcp.test.ts`, calls every handler) |
| 5 | The proxy refuses to bind every interface by accident | `npm test` (`bind.test.ts`) |
| 6 | Gateway mode rejects callers without the shared token | `npm test` (`proxy.test.ts`) |
| 7 | `apis.yaml` contains no guessed prices | `skeletonkey apis validate` + `apis.test.ts` |

## Scenarios

Three end-to-end walkthroughs. For each step: the SkeletonKey MCP tool used, and
whether **v0.1 automates it** or a **human does it**.

Legend:

- **auto (SkeletonKey)** — SkeletonKey v0.1 does this.
- **auto (agent)** — the agent's own tools do it; SkeletonKey neither helps nor
  hinders.
- **manual (human)** — a person acts. Non-negotiable for payment and the final
  terms confirmation.

### Scenario A — "agent needs X/Twitter data"

The user asks their agent to summarise what a set of accounts posted this week.

| Step | What happens | Tool | v0.1 status |
| --- | --- | --- | --- |
| 1 | Agent recognises it needs social data and checks SkeletonKey instead of asking for a key | `find_api("social data")` | **auto (SkeletonKey)** — returns `example-x-twitter-api`, `access_mode: own-account`, `min_topup: null` (unknown), `signup_automatable: null` |
| 2 | Agent asks whether access already exists | `request_access(platform="example-x-twitter-api", reason="summarise weekly posts", est_budget=null)` | **auto (SkeletonKey)** — `has_key: false`, plus a signup plan |
| 3 | Agent reads the plan's caution: X has historically gated API access behind developer-portal approval and the terms are unreviewed, so automated signup is **not** cleared | — | **auto (SkeletonKey)** — the caution is in the response |
| 4 | Agent reports this to the user and asks whether to proceed | — | **manual (human)** — the user decides |
| 5 | Developer-portal application: project description, use case, approval wait | — | **manual (human)** — not automatable in v0.1, and plausibly never |
| 6 | Human accepts the developer terms and any paid tier with their own card | — | **manual (human)** — SkeletonKey code never sees card data |
| 7 | Agent asks for the key to be registered; the human types it on their own terminal | `register_key(alias="x-personal", platform="X", domain="api.x.com")` | **auto (SkeletonKey)** for the prompt and storage; **manual (human)** types the key |
| 8 | Agent gets the proxy URL | `request_access(platform="X")` → `has_key: true` | **auto (SkeletonKey)** |
| 9 | Agent calls `http://127.0.0.1:8787/api.x.com/2/tweets?...` with no credential; the proxy injects `Authorization` | — | **auto (SkeletonKey)** |
| 10 | Agent reports what the task used | `ledger("x-personal")` | **auto (SkeletonKey)**; `cost_usd` is `null` unless X reports a price header, which it does not — so spend is reported as unknown |

**Honest summary:** v0.1 removes the key-handling problem entirely and tells the
agent to stop before the approval gate. It does not get you through X's
developer-portal review; nothing can.

### Scenario B — "agent needs web scraping via Apify"

The user asks their agent to extract structured data from 200 product pages.

| Step | What happens | Tool | v0.1 status |
| --- | --- | --- | --- |
| 1 | Agent looks for a scraping API | `find_api("web scraping")` | **auto (SkeletonKey)** — matches `example-apify-scraping`, `domain: api.apify.com` |
| 2 | Agent checks for existing access | `request_access(platform="example-apify-scraping", reason="extract 200 product pages", est_budget=5)` | **auto (SkeletonKey)** — `has_key: false` + plan. `est_budget` is recorded as the *agent's estimate*, never treated as a price |
| 3 | Agent reads the caution that scraping terms belong to the target site as well as to Apify | — | **auto (SkeletonKey)** |
| 4 | Agent opens `https://docs.apify.com` / the signup page in its own browser | — | **auto (agent)** — the agent's computer-use tool, not SkeletonKey |
| 5 | Agent signs up as `apis+apify@example.com` (the `+alias` SkeletonKey suggests) | — | **auto (agent)** — SkeletonKey supplies the address, the agent does the typing |
| 6 | Agent reads the verification code from its own email connector and verifies | — | **auto (agent)** — SkeletonKey has no email access by design |
| 7 | Agent reaches the plan/payment screen and **stops** | — | **manual (human)** — the human picks the plan and enters their own card |
| 8 | Human accepts the Apify terms — the final confirmation | — | **manual (human)** |
| 9 | Human creates the API token in the dashboard; agent calls `register_key` and the human types it straight into the vault | `register_key(alias="apify-personal", platform="Apify", domain="api.apify.com")` | **auto (SkeletonKey)** for prompt + storage; the key never enters the agent's context |
| 10 | Agent calls `http://127.0.0.1:8787/api.apify.com/v2/acts/...` and starts the run | `request_access` for the URL | **auto (SkeletonKey)** |
| 11 | Mid-run, the user wants to know the damage | `ledger("apify-personal")` / `key_status("apify-personal")` | **auto (SkeletonKey)** — call count and bytes are exact; `cost_usd` is `null` because Apify does not report per-call cost in a header |
| 12 | Job done, key not needed again this month | `disable("apify-personal")` | **auto (SkeletonKey)** — injection stops, the secret stays in the vault |

**Honest summary:** this is the scenario v0.1 serves best. Steps 4–6 are real
automation, but they are the *agent's* capabilities — SkeletonKey's contribution is
the plan, the hand-over points, and never touching the key.

### Scenario C — "agent needs embeddings via Voyage"

The user asks their agent to build a semantic index over a local document set.

| Step | What happens | Tool | v0.1 status |
| --- | --- | --- | --- |
| 1 | Agent needs an embeddings provider | `find_api("embeddings")` | **auto (SkeletonKey)** — matches `example-voyage-embeddings`, `domain: api.voyageai.com` |
| 2 | Agent checks for a key | `request_access(platform="example-voyage-embeddings", reason="index 4k documents", est_budget=2)` | **auto (SkeletonKey)** |
| 3a | **If a key already exists** (the common repeat case): response is `has_key: true`, `alias`, `injected_header`, `proxy_url` | `request_access` | **auto (SkeletonKey)** — total elapsed: one tool call, no human |
| 3b | If not: signup plan, same shape as Scenario B | `request_access` | steps 4–9 of Scenario B apply |
| 4 | Agent sets its embeddings client's base URL to `http://127.0.0.1:8787/api.voyageai.com` and leaves the API-key field empty or a dummy | — | **auto (SkeletonKey)** — the proxy strips the dummy and injects the real header |
| 5 | Agent embeds in batches; each call is one ledger row | — | **auto (SkeletonKey)** |
| 6 | Agent checks spend before a second large batch | `key_status("voyage-personal")` | **auto (SkeletonKey)** — exact call count, `cost_usd: null` unless reported |
| 7 | User asks "what did this cost?" | `ledger("voyage-personal")` | **auto (SkeletonKey)** — reports calls and bytes; says spend is **unknown**, not zero |

**Honest summary:** once the key exists, this is the whole point — the agent goes
from "I need embeddings" to a working, credential-free call in one tool call, and
the key never leaves the vault.

## What these scenarios show v0.1 does *not* do

- It cannot pay. Step 7 of Scenario B and step 6 of Scenario A are hard stops.
- It cannot tell you what a call cost, for almost any provider. It can tell you
  exactly how many calls were made and refuses to invent the rest.
- It cannot promise that automated signup is permitted. `apis.yaml` records what
  a human verified; in this repo that is nothing, so every row says so.
- It does not drive the browser or read email. Those are the agent's own tools.
  If your agent lacks them, v0.1 degrades to "the plan, printed", and the human
  does the signup.
