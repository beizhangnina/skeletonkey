Let your agent get its own API access — without ever handing it your keys.

Your agent can find the API it needs, sign up for it and call it. Your passwords, your API keys and your card never reach the model. You set the ceiling on what it can spend, and the decisions that cost money wait for you.

Free and open source under the MIT license. Nothing to sign up for.

Install

01 — The problem

Why it exists

An agent is only as capable as the things you are willing to give it a key to.

Paste a key into a prompt or a config file and a model is holding a credential you cannot take back. It can spend against your account. If the service needs a new account first, that means your email, your password and your card as well.

So the safe answer has been to hand over nothing, and let the work stop at the edge of what the agent can already reach.

02 — What you get

Four things
  • 01

    Access it can get for itself

    Your agent asks for a capability — scraping, geocoding, transcription — and comes back with a working route to a provider. If the provider is new to it, it can take the whole signup from the first page to the first call.

  • 02

    Your keys never reach the model

    Passwords, API keys and card details stay where you keep them. They are never part of a prompt, a tool result or anything the agent can read back. It gets the door opened, not the key.

  • 03

    A ceiling you set

    Give it a spending cap and it works under that cap. Anything that costs real money — a paid plan, a card, a set of terms — stops and waits for you to agree to it yourself.

  • 04

    On your machine, not ours

    There is no account and no SkeletonKey service in the middle. Your keys stay on your own disk, and every call your agent makes is written down there for you to read.

04 — Quick start

Five steps
  1. 1

    Install

    No SkeletonKey account and no server. You set a local passphrase, and init registers the MCP server and skill for Claude Code and Codex.

    $ npx -y @dormy/skeletonkey init

    Not on npm yet. How to install it today.

  2. 2

    Find an API

    Browse the directory yourself, or let your agent search the same local index:

    find_api("web scraping")
  3. 3

    Create the vendor accountcoming in v0.4

    Your agent starts the signup. You finish the captcha, the terms and the payment yourself, in your own browser, then hand it back:

    $ skeletonkey signup start <vendor>
$ skeletonkey signup complete <vendor> --account <name>

    The key is entered through a hidden input straight into your vault — never into a prompt or a tool result.

    Already have a key for this vendor?

    $ skeletonkey account add <name> --vendor <id> --store-key --domain <d>
  4. 4

    Use it

    From here your agent just calls the API. Every call goes through the local proxy, which injects the key at request time — the agent never sees it.

  5. 5

    Weekly monitoringcoming in v0.4

    A scheduled check sends a system notification if it finds an anomaly, and writes a redacted report you can read without exposing a key:

    $ skeletonkey monitor run

    Read the latest report

    $ skeletonkey monitor report --latest

Your agent gets the access. You keep the keys.

05 — The detail

v0.1 notes
What is the security model?

No tool SkeletonKey gives your agent returns a key. The agent calls a loopback proxy on 127.0.0.1, the proxy injects your key for that destination domain on the way out, and a SQLite ledger records one row per call. The key is never in the agent's context, so there is nothing for it to leak, log or reuse.

When an API needs a new account, the agent walks the signup with its own browser and its own email address, and stops at payment and terms. You confirm those yourself.

Where do the keys live, and how are they resolved?

In a vault on your own machine: Bitwarden by default, or 1Password, your operating system keychain, or an encrypted file. There is no account and no SkeletonKey server, so nothing of yours is stored anywhere we can reach.

A secret is resolved by name out of the backend you configured, at the moment a call is made, and handed only to the local proxy — never to a tool result, a prompt or the ledger. A key leaves your machine only on the request you asked the proxy to make, addressed to the provider it belongs to.

What does my agent actually talk to?

An MCP server and a skill that run locally, which is why Claude Code and Codex can use it with one line of configuration. The tools are deliberately narrow: find an API, request access to one, record a provider SkeletonKey does not know yet. None of them can hand back a credential.

How does it find an API it has never used?

find_api("web scraping") searches an index on your disk, seeded with 163 providers. On a miss, discover_api and propose_entry add the vendor to your own local index, so the next search finds it. Nothing about that is sent anywhere.

How do I install it today?

npm publishing is off for v0.1, so the two npx lines above are the target, not a working install yet. Build it from source instead. It needs Node 22 or newer.

From source

$ git clone https://github.com/beizhangnina/skeletonkey.git
$ cd skeletonkey && npm install && npm run build && npm link
$ skeletonkey init  # alias: skk
How is this different from a key aggregator?

An aggregator is a service you sign up for that fronts many APIs through its account and its billing. SkeletonKey fronts nothing and holds nothing: you keep your own provider accounts and your own keys, and calls go direct through a proxy on your machine.

The local index recommends an aggregator route only when going direct would mean taking out a subscription.

What does it cost?

The open source path is free. v0.1 is MIT licensed and runs entirely on your own machine, so the only bills are the ones from the APIs you sign up for. The hosted endpoint is not built, so it has no price and no date.
